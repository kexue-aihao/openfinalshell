## 0.30.27 更新内容

Android 端新增**本地终端**：在本机上直接开一个 shell，按设备能力分三档权限。

- **三档权限**。应用自身（`/system/bin/sh`，无需任何设置）、ADB shell（uid 2000，经 Shizuku）、root（uid 0，经 Shizuku-as-root 或 `su`）。档位在**每次连接时重新探测**，不缓存 —— 重启会让 root 与 Shizuku 一起消失，缓存下来的答案只会让卡片撒谎。
- **终端、文件、监控、AI 助手全部接入本地会话**。本地会话实现的是同一个 `SshTransport` 契约、注册进同一个会话注册表，所以上述四个面板的调用点一行未改，改动集中在传输层与终端层。
- **PTY 是真的**。`libtermux.so` 随包提供真实的 `forkpty` 能力，应用档直接用它；ADB/root 档由自研的 `libofspty.so` 在特权进程里分配。之所以必须自己写：Termux 那套 JNI 在静态初始化里写死了 `System.loadLibrary("termux")`，而 `loadLibrary` 只按路径搜索、不查已加载集合，出了应用进程必然 `UnsatisfiedLinkError`。
- **删除护栏**。本地递归删除是唯一能毁掉用户设备的操作。桌面端「路径至少两级」的规则不能照搬：`/data` 只有一级，而 `/storage/emulated/0` 有四级却是用户全部共享存储。改以受保护子树 + 挂载点 + 可写根白名单为准，并**全程以 canonical 路径判定** —— `/data/user/0/<包名>` 会被解析成 `/data/data/<包名>`，用原始路径比对会把应用自己的目录判成禁区。
- **root 档的额外闸门**。构建开关之外还要在设置里显式开启；每次连接前弹确认，讲清楚 uid 0 能读到本应用保存的连接与 AI Token；确认只存在内存里，进程重启必然重问；AI 助手往 root 会话写命令时会在协程内复查一次，避免撤回确认后被过期界面绕过。
- 本地会话是设备专属的，**不进导出、也进不了局域网同步**；导入侧还会拒绝被塞进文件里的本地会话。

### 验证与开放范围

已实测（API 35 x86_64 模拟器）：

- 33 项仪器测试全通过，含 9 项本地终端、7 项对真实 native 宿主的协议测试、4 项 Shizuku ADB 档端到端；另有 138 项单元测试、i18n 校验、lint（0 error）、Debug 与 Release 各 5 个 APK 构建通过。
- Shizuku 档端到端证实：shell 的 uid 是 **2000 而非应用自身**，`/sdcard` 可列，`/proc/net/tcp` 可读（监控的 TCP 状态段在该档下才变得可用）。
- 跨 uid loopback 已证实：应用 uid 的进程能驱动 shell uid 的 PTY 宿主。这一条原本只是架构假设 —— SELinux 完全可能拒绝，而一旦拒绝整个特权档设计就塌了。

仍待验收：

- **root 档在真机上的表现**。没有已 root 的设备，`su` 路径从未运行过；Sui/Shizuku-as-root 走的是已验证的同一条路径。
- **PTY resize 是否到达内核**。模拟器镜像没有 `stty`，该断言保持自跳过；视口那一半有独立断言。
- Android 8/9/10：启动 Shizuku 需要电脑 ADB，界面已按 API 级别给出不同提示，但未实测。

### 发布过程记录

本轮有两个 bug 只有真跑一次才会暴露，都不是读代码能发现的：

1. **`ShizukuProvider` 根本不在 manifest 里**。Shizuku 通过查询每个客户端应用的 `<包名>.shizuku` provider 把 binder 交回去，而我误以为 `dev.rikka.shizuku:provider` 这个依赖会自己声明它 —— 不会。后果是 ADB 档对**所有用户**都不可用，且不报任何错：`pingBinder()` 永远是 false，界面只显示「Shizuku 未运行」，看起来像用户没配好。线索来自服务端日志的 `provider is null`。已按官方样例声明，并注明 `INTERACT_ACROSS_USERS_FULL` 才是把它挡在普通应用之外的那道闸。
2. **helper 返回的是 `waitpid` 的原始状态字，不是退出码**。shell `exit 3` 报回来的是 768（3 << 8）。监控不检查退出码所以没事，但打包传输那条路径会检查，每个命令的退出码都会错 256 倍。已改为按 shell 惯例解码。

顺带补齐的一处产品缺口：此前实现只**检查** Shizuku 授权、从不**申请**，所以那个权限永远不可能被授予。现已补上申请路径，并在卡片上把「缺少 Shizuku 授权」渲染成按钮而非文字。

本次只改 Android 端、Android CI 工作流与 `.gitignore`（新增 NDK 中间产物 `android/.cxx/` 的忽略项），桌面端功能代码未改动。

### 发布过程记录

首次推送 tag 后 Android 与桌面两个发布工作流都失败了。原因分别是：

1. **`android-release.yml` 从来没装 NDK。** 本功能让 `:app` 依赖 CMake/NDK 构建特权 PTY 宿主（`ndkVersion` + `externalNativeBuild`），而我只给 `android.yml` 加了 NDK。NDK 缺失时 `:app` 连配置阶段都过不去，所以该 job 里**任何** Gradle 任务都会失败，而不是只有 native 那个。两处现在都装，并且**装完立刻校验** `ndk/<版本>/source.properties` 与 `cmake/<版本>/` 存在 —— 静默空装必须在 SDK 那一步就报出来，不能伪装成一个看不出因果的 Gradle 错误。
2. **`:core:testDebugUnitTest` 失败于 `LocalFileChannelTest > deleteRefusesPathsOutsideTheWritableRoots`** —— 是**测试自己的 bug**，不是护栏。该用例建了 `outside/` 与 `outside/allowed`，却从没建它要删的 `outside/a.txt`；`delete()` 在路径不存在时先抛 `IOException`，护栏根本没被走到，于是断言的是另一个错误。它之所以长期没暴露，是因为被 `posixOnly()`（`assumeTrue(File.separatorChar == '/')`）挡在 POSIX 主机之外，在 Windows 开发机上**从未执行过**。修法是先建出目标文件，并补两条断言：护栏确实拒绝（`PROTECTED_PATH`），且**被拒绝的删除不能删掉任何东西**；同一场景另加一份仪器测试，Android 内核就是 Linux，这条路径以后在每个设备上都会跑到，不会再被平台开关藏住。
3. 修 1 的过程中自己引入了一个：`yes | sdkmanager --licenses` 在 Actions 的 `bash -eo pipefail` 下必然失败（sdkmanager 停止读取后 `yes` 收到 SIGPIPE），实测 17 秒即挂。已加 `|| true`。

诊断过程本身也补了一处缺口：该 job 在 Actions 界面上无法回答"为什么失败"，而日志接口要仓库 admin、产物下载要认证。现在失败步骤会把 gradle 输出里带 `> Task … FAILED`、`FAILED$`、`AssertionError` 的行转成 `::error::` 注解，**注解是公开可读的**，所以 CI 独有的失败不再需要维护者本地复现；同时失败时会打包 `reports/` 与 `test-results/` 作为产物。上面的用例名就是靠这个拿到的。

`v0.30.27` 的 tag 由首次推送的位置（`36fce27`）移到了修正后的 `213e9f6`：旧位置上那次运行不可能成功，而发布工作流不重推 tag 不会重跑，且当时**没有任何 Release 或产物被创建**，没有需要回退的发布。重推后 Android 与桌面两个工作流均通过，Release 产出 31 个产物（Android 5 APK + AAB + 校验和，Windows/macOS/Linux 各架构安装包与自动更新 feed）。
